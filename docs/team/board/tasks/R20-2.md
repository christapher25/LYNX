## Exact behaviour

### (a) Guard: empty-column dtype change, corporate_actions ONLY
Fact measured by LEAD on the real snapshot (logs/history_guard/corporate_actions.json): for the drifted columns, the snapshot digest equals `_digest_series(pd.Series([None]*n, dtype=object))`, n = the unit's row count; today the column is float64 or datetime64[us] with zero non-null values in the rows dated <= 2026-09-29.
1. The snapshot format and every existing digest stay exactly as they are. No re-snapshot, no change to `_digest_series`. An existing snapshot must verify without being rewritten.
2. Units computed NOW for the corporate_actions dataset carry one extra key, `"all_null": [sorted names of columns with zero non-null values in the history rows]`. It is not part of any digest. Other datasets do not get it. (Writing it into new snapshots too is fine; old snapshots lack it and that must not matter.)
3. In the comparison, for name == "corporate_actions" only, a column whose digest differs is NOT a failure iff BOTH hold: (i) the snapshot digest equals the digest of an all-null column of the snapshot's row count in one of these representations: object all-None, object all-NaN, float64 all-NaN, datetime64[ns] all-NaT, datetime64[us] all-NaT; (ii) the column is in the new unit's `all_null`. It is then reported as ALLOWED with the text "empty column changed stored type" and the column names.
4. Everything else stays strict and unchanged: row count, the ex_date digest ("keys"), the column set, and any column that held even one non-null value at snapshot or holds one now in history rows. `adjusted`, `universe`, `features_*`, `indicators` get no such tolerance (same input must still FAIL there).

### (c) Guard: owner-approved expected changes
1. New optional argument on `verify`: `--expected-changes PATH` (a JSON file; LEAD supplies it; format below). Without it behaviour is exactly as today.
   {"history_cutoff": "2026-09-29", "actions": [{"symbol": "AASTHA", "ex_date": "2026-09-28", "action_type": "bonus", "adjustment_factor": 0.5}, {"symbol": "AAATECH", "ex_date": "2026-09-23", "action_type": "dividend", "adjustment_factor": null}, ...]}
   Extra top-level keys are ignored. A malformed file, or `history_cutoff` different from the snapshot cutoff: exit 1 with a FAIL line, nothing verified silently.
2. corporate_actions, symbol with expected actions: read the current file, take the history rows, remove exactly the rows matching an expected entry on (ex_date, action_type, adjustment_factor; null factor matches null; float compared after round(…, 12)). Each expected entry must match exactly ONE row, else FAIL naming the entry (zero rows = "expected action not present", more than one = "ambiguous"). The remaining rows are then compared with the snapshot under the normal rules plus (a). Pass: report ALLOWED "N owner-approved action(s) added" with the entries. So exactly the approved rows are new and every other history row is still proven unchanged.
   Because removing rows can leave a column's pandas dtype different from the snapshot's, rule (a) applies to that remainder as well; nothing looser.
3. adjusted: a symbol with an expected action whose adjustment_factor is not null is added to the set of symbols whose ADJ_* / ADJUSTMENT_APPLIED columns may differ (the existing `allowed_adj` set), reported ALLOWED with the text "owner-approved correction". Unadjusted columns, row count and dates of that symbol stay strict. A symbol with only null-factor expected actions (dividends) gets NO adjusted exemption.
4. An expected entry for a symbol with no corporate-actions unit now: FAIL.
5. The verify log prints, at the end, the three ALLOWED kinds as separate counts (new-action adjusted, empty-column type, owner-approved).

### (b) Ingester: the refresh keeps each file's stored schema  (after R20-1 is merged)
In `refresh_symbol`, before the atomic write:
1. Read the existing file's Arrow schema (pyarrow.parquet.read_schema). Write the merged frame with that schema, field by field, with one exception: a field whose stored Arrow type is `null` AND for which an added row has a non-null value takes the type of the added values (this is the unavoidable case that guard rule (a) covers).
2. So: a column with a non-null stored type keeps that exact type even if the added rows are all-null objects; a `null`-typed column stays `null` when the added rows are also all null there; column order and names are unchanged.
3. If an added value cannot be cast to a non-null stored type without loss or error: the symbol is `failed`, the file is untouched (same path as a write failure).
4. History rows are byte-for-value identical after the write (the existing merge-only tests must still pass). A rerun that finds nothing new still writes nothing.
pyarrow is already a dependency; no new dependency.
