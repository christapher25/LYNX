# R20-10: data_refresh fails at the announcements step when --start falls inside an existing chunk

Lane: DEV-B. Branch: row20/refresh-announcements-range (from main ead0771). Depends on: nothing. Start now.

## What happened (LEAD's real run, job data_refresh run 20261112_155158, exit 1 after 2 min 19 s)
Eight ingester steps succeeded (newest on disk 2026-11-11 for bhavcopy, bhavdata, fno_bhavcopy, fno_ban, sec_list, price_band_hits, indices, fii_dii). The announcements step was called with `--start 2026-11-09`. data/ingest_announcements.py stores range chunks (announcements_<start>_<end>.parquet); a chunk announcements_2026-11-01_2026-11-09.parquet exists, so the ingester refused the range 2026-11-09_2026-11-11:
  "2026-11-09_2026-11-11: partially overlaps ['announcements_2026-11-01_2026-11-09.parquet']; refusing to write duplicates (align the range to those files)"
and wrote a manifest record {"trade_date": "2026-11-09_2026-11-11", "status": "failed", "error": "partially overlaps existing [...]"}. The wrapper then (correctly, by its own rule) failed the step: "the manifest records `failed` for 1 date(s) ... ['2026-11-09_2026-11-11']". The downstream chain did not run (correct).
Two problems for a weekly job: (1) any --start that falls on or before the end of the newest chunk makes the step fail; (2) that failed record's key will never be re-run successfully (the aligned rerun has a different key), so it would fail every later run whose window overlaps it.

## Exact behaviour
1. Range-chunk steps (today only `announcements`; make it a Step attribute, default False): before building the child command the wrapper reads the chunk files on disk for that step and takes E = the latest chunk END date. The step's effective start = the later of (--start) and (E + 1 day). If the effective start is after the step's end date (yesterday, as the ingester defaults): the step is logged "already current through E" and counts as succeeded without running a child. Otherwise the child is called with the effective start. The other steps are untouched.
   Chunk file names that do not parse as <prefix>_<YYYY-MM-DD>_<YYYY-MM-DD>.parquet are ignored with a WARNING; if NO chunk parses, the step runs with --start unchanged.
2. Superseded overlap refusals: in the manifest check, a `failed` record is EXCUSED only if ALL hold: (a) the step is a range-chunk step; (b) its error text starts with "partially overlaps existing"; (c) its key is a range a_b with valid dates; (d) every calendar date from a to b inclusive lies inside the [start, end] range of at least one chunk FILE on disk for that step. Then the dates are all stored and the refusal lost nothing. It is logged as "excused: overlap refusal superseded by chunks on disk" with the key and the covering files. Anything else stays a failure: another error text; a date in the range not covered by any file; a non-range key; a non-range-chunk step.
   Note the order: after rule 1 runs the aligned range (2026-11-10..) and its chunk exists, the old record 2026-11-09_2026-11-11 becomes fully covered and is excused. If the aligned fetch fails, 2026-11-10 and 2026-11-11 are not covered and the old record still fails the step (correct).
3. Rule 2 is evaluated after the "not yet published" rule (first date >= today) and independently of the stale re-serve excuse; one record needs only one valid excuse; the summary lists each excused key with its reason.
4. No file is written, moved or deleted by the wrapper for this; the manifest is never edited.
